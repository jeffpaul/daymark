# Daymark — UI/UX Polish History

> Extracted from CLAUDE.md's own architectural-decisions table to keep that
> file focused on load-bearing architecture — the facts a contributor or a
> new Claude Code session needs before touching code — rather than every
> narrow visual fix along the way. CLAUDE.md is auto-loaded as project memory
> for every session on this repo; this file is read on demand, so moving
> pure polish/refinement history here costs nothing to a session that doesn't
> need it, while still keeping the reasoning available (and reusable as
> precedent) for one that does.
>
> Grouped by theme, not strictly chronological — several rows below cite an
> earlier row in the *same* theme as precedent (e.g. a later header-alignment
> fix reusing the same negative-margin technique an earlier one introduced),
> so reading a theme's own rows top-to-bottom tells that theme's story in
> order. Each row is unchanged from its original CLAUDE.md table entry.

## Superseded: Timeline inline-expand era

| Decision | Value | Rationale |
|----------|-------|-----------|
| Timeline card inline expand (Unreleased) | Tapping a Timeline card — a Mark, an ordinary block-editor post, or a subscription post — expands its own content directly below the card, in place, instead of the old behavior (a Mark/post navigated away to its real permalink; a subscription post opened a modal/overlay `.daymark-sheet` dialog). `toggleExpand()`/`closeOpenExpand()` (`assets/app.js`) are the one shared mechanism for both card kinds, only one panel open per screen at a time. A Mark or ordinary post's content comes from a new `GET /marks/{id}/content` (not gated on `_daymark_is_mark`, matching `GET /timeline`'s own inclusive Marks query) which renders straight from `post_content` via `apply_filters( 'the_content', ... )` — the same core filter a theme's own `the_content()` call runs, applied to one post in isolation rather than the whole page a permalink visit would render around it, so there's no comments/nav/header/footer to accidentally include in the first place. A subscription post's content still comes from the existing external click-through fetch (`GET /subscription-posts/{id}`), whose own extraction (`Daymark_Subscription_Poller::extract_body_html()`) was hardened alongside this: it now also strips `<nav>`/`<header>`/`<footer>`/`<aside>` wherever they appear and prefers the fetched page's own `<article>` element over its whole `<body>`, with a defensive second pass dropping anything from a recognizable `id="comments"`/`id="respond"` container onward — a bounded, regex-based approximation (this codebase's established choice over a DOMDocument dependency), not full Readability-style article extraction. | Directly the requested behavior: expanding in place shows more of the Timeline at a glance and never yanks the reader out of the app, while a permalink-navigation or a modal both did. Reusing `post_content` + `the_content` for a Mark/ordinary post is a strictly better fix than extending the subscription poller's own page-scraping approach to the site's own content would have been — there's no fetched page to narrow down when the content already lives in this site's own database, so the "don't show nav/header/footer/comments" guarantee is exact for that half rather than heuristic. The subscription half can't have that same exactness (it's someone else's page, structure unknown), so it gets the best bounded heuristic this codebase's no-DOMDocument constraint allows, same tradeoff already accepted for its script/style stripping. |
| Timeline inline-expand: card frame, skip-link stripping, permanent "open original" icon, hover tooltips (issue #196) | Four related fixes. **Card frame**: `.daymark-recent__item-wrap:has(.daymark-recent__expand:not([hidden]))` (`assets/app.css`) gives the whole item — icons, card, and the expand panel together — a visible border/background/padding while expanded, so opening a card reads as its own frame growing taller rather than as content inserted between Timeline items (a collapsed card still has no such border, matching every other item). **Skip-link stripping**: `Daymark_Subscription_Poller::extract_body_html()` gained a 5th pass stripping a leaked accessibility "Skip to content" link from a subscription post's click-through content — the existing `<article>`-preference pass doesn't exclude it when a site has no `<article>` element at all and falls back to the whole `<body>`, which still includes it (conventionally the very first element there). Matches both the common direct-text shape (`<a href="#content">Skip to the content</a>`) and any anchor whose own `class` marks it as a skip link. **Permanent "open original" icon**: the "View full post"/"View original" link that used to live in the expanded content's own footer (`expandBodyHtml()`) is now `renderExternalLinkToggle()` — a 6th, permanent stat-row entry between Bookmark and Share, using the same `span[role="button"]` pattern, so opening the source is available even on a collapsed card, not only once expanded. Its own URL lives directly on the element (`data-external-link`), simpler than Share's `screen`-map lookup since there's no second field (a title) it also needs. `expandBodyHtml()` no longer takes or renders a permalink/label at all. It's rendered in `renderItemStats()` — the stat row shared by every published Mark card, not only a subscription post's — so a Mark you published to your own site gets it too, opening its own permalink; confirmed deliberately with Jeff rather than left as an unflagged scope expansion, since "View original" previously existed only in a subscription post's expand footer. **Hover tooltips**: every icon in the row (`renderStat()`'s three read-only stats, Bookmark, "open original", Share) now carries a `title` attribute mirroring its `aria-label`, matching the precedent `renderSiteIconButton()` already set — a native `title` costs nothing on a touch device (it simply never triggers there), so no separate touch-detection was needed. | The card-frame fix is a pure `:has()` CSS addition — no JS/markup change — matching this codebase's established "state-scoped styling via `:has()`" precedent (e.g. the ⋯-menu open-state z-index rule). Reusing the `<article>`/`<body>` fallback's own known gap (already documented in that method's docblock) to explain *why* the skip link leaks, rather than guessing at a new root cause, kept the fix targeted at the actual reported symptom instead of a broader, riskier rewrite of the extraction logic. Promoting "open original" to a permanent icon (rather than leaving it conditional on expansion) directly serves the request's own framing — a reader who just wants the source shouldn't have to expand the whole card first — and reusing the exact toggle pattern Bookmark/Share already established kept the row's six entries behaviorally uniform rather than adding a third interaction convention. Including it on a Mark's own card (not just a subscription post's) keeps the row's icon set identical everywhere rather than having it appear or disappear depending on card kind — a Mark's permalink is cheap to have on hand regardless, and jumping to the live, theme-rendered page is occasionally useful even for your own content (checking how it actually reads to a visitor, copying its URL). |
| Expanded card visually separates borrowed content from Daymark's own chrome (issue #221) | The expanded card frame's own background (`.daymark-recent__item-wrap:has(.daymark-recent__expand:not([hidden]))`, `assets/app.css`) changed from `var(--daymark-surface)` (gray) to `var(--daymark-bg)` (white) — the same white every other card already has. `.daymark-expand-content` itself now carries `var(--daymark-surface)` plus its own padding/border-radius, so the gray tint moved onto the borrowed post content specifically. The "Reply" action on a subscription post's expand panel (`loadSubscriptionExpandHtml()`, `assets/app.js`) was already rendered as a sibling *after* `.daymark-expand-content`, not nested inside it — no markup/JS change needed, only which element carries which background. | Reported as "the Reply link reads as part of the source page's own content" — the structural separation (Reply as a sibling, not nested) already existed; the actual gap was purely visual, since both ended up the same shade of gray with nothing distinguishing them. Moving the gray tint onto `.daymark-expand-content` alone (rather than, say, adding a border around Daymark's own chrome) directly marks the *borrowed* content as the exception, matching how every other card's normal white background reads as "this is Daymark," not needing every one of Daymark's own elements to carry a distinguishing style. |

## Header chrome

| Decision | Value | Rationale |
|----------|-------|-----------|
| Header Daymark icon size/chrome polish (PR #192) | A follow-up to "Header chrome shared across Home/Explore/Search/Me" above: the Daymark icon grew from 22px (Home's wordmark) / 20px (Explore/Search/Me's icon-only link) to 26px on both, closer to the visual weight of the bottom nav's own 22px icons — the app icon's own baked-in padding/rounded corners meant it read smaller than a line-icon glyph at the same nominal size. Explore/Search/Me's icon link also drops the bordered-square `.daymark-iconbtn` button chrome via a new `.daymark-iconbtn--plain` modifier (`border-color: transparent; background: none;` — kept as a modifier rather than changing `.daymark-iconbtn` itself, and `border-color` rather than `border: none`, so the box's own dimensions/centering stay identical to a bordered button) so it reads as plain as Home's own unboxed wordmark icon; the Notifications bell right next to it on those same headers keeps its bordered square unchanged — the modifier is scoped to the Daymark icon link alone. | Directly the requested polish. A modifier class (rather than a second, separate icon-link helper function or a bespoke one-off style) keeps `daymarkIconLink()` as the one shared render function Explore/Search/Me all still call, matching the "one shared mechanism" pattern CLAUDE.md's own "Header chrome shared across Home/Explore/Search/Me" row already established for this exact chrome. |
| Explore/Search/Me header icon left-edge alignment (issue #276) | A further correction to the "Header icon/title spacing" fix in "Timeline polish batch (issue #267)" above: making the icon-to-*title* gap provably equal (via `.daymark-iconbtn--plain`'s `justify-content: flex-end`) left a second, separate gap unaddressed — the tap target's own 18px leading overhang (44px `--daymark-tap-min` box minus the 26px icon) shifted the icon graphic itself, and everything after it, 18px right of where Home's `.daymark-homelink` icon starts, since Home has no such wrapping box. `margin-left: calc(26px - var(--daymark-tap-min))` on `.daymark-iconbtn--plain` cancels exactly that overhang. That alone left a residual 1px still off (confirmed both in CI's own pixel measurement and a live-preview screen recording): under this file's global `box-sizing: border-box`, `.daymark-iconbtn`'s inherited `border: 1px solid` still reserves its 1px on every side even once `border-color` alone is overridden to transparent, shrinking the content box the flush-right icon sits in by 2px total — `border: none` (replacing the color-only override) removes that reservation instead of just its paint, with zero change to the box's own 44px outer footprint (`min-width` sizes the border-box either way). Verified pixel-exact with a static side-by-side repro (both header markups rendered against the same `app.css`, screenshotted headlessly, edge positions measured programmatically) rather than only reasoning about the CSS or eyeballing a screenshot, since this exact spot had by then been "fixed" three times without actually landing pixel-perfect. | The same "negative margin cancels a box's own reserved space" pattern already used for `.daymark-pullrefresh` (issue #213) and `.daymark-timeline-flourish--start`/`--end` (issue #267) — a box that reserves width for a required tap target but doesn't want that width to visually count against its neighbor's position pulls itself back by exactly the amount it doesn't use. Three prior passes at this exact header (PR #192, then issue #267, then this issue's own first commit) each closed one remaining gap without catching the next one hiding underneath it — a gap, then an 18px absolute-position offset, then a 1px border-box artifact of the very type used to fix the gap. Moving from "reason about the CSS" to "measure the rendered pixels" is what finally caught the last of these; a value meant to be *identical* across two screens is worth verifying that way from the start next time, not just visually approximated. |
| Full-screen post view's back arrow/icon top-aligned against a wrapped title (issue #315) | `PostScreen`'s header (`assets/app.js`) reuses the shared `.daymark-topbar` class every other screen's header uses (Home, Search, Explore, Me, Notifications) — but unlike those, whose title is a short, fixed, always-single-line string, `PostScreen`'s title is the post's own and can be arbitrary length, so it's the one header that can wrap to two or three lines. `.daymark-topbar`'s base `align-items: center` centers the back link against the *whole* title block in that case, leaving the arrow/icon floating at the visual midpoint of a wrapped title instead of level with its first line — reported directly against a real long title ("Agency workflows, components, and highlights from WCUS"). **Fixed** with a new `.daymark-topbar--top { align-items: flex-start; }` modifier (`assets/app.css`), added to `PostScreen`'s own `<header>` only — every other screen's single-line title still reads correctly centered under the shared base rule, so the fix is scoped rather than changing `.daymark-topbar` itself. Verified with a Playwright-rendered before/after screenshot against the real `app.css` and the exact reported title text, not just CSS reasoning alone. | Matches this codebase's own established precedent (`.daymark-backlink--icon`, `.daymark-iconbtn--plain`) of a scoped modifier class over a shared-rule change whenever only one of several screens sharing a base class is actually affected — the other seven `.daymark-topbar` headers have no reason to ever wrap, so centering is still correct for them. Measuring the actual rendered pixels (rather than trusting the CSS reasoning alone) follows the explicit lesson CLAUDE.md's own "Explore/Search/Me header icon left-edge alignment (issue #276)" row already drew from three successive "reasoned" alignment fixes each missing a residual gap the next one caught — worth doing here too before calling a visually-sensitive fix done. |
| ⋯ overflow menu floats instead of growing the card's frame open; header chrome tightened (issue #347) | Reported directly, with screenshots. **Overflow menu**: `.daymark-recent__overflowmenu` (issue #326) previously grew the item's own frame open, the same full-width-row treatment the Routing popover still uses — reported as wrong specifically for the ⋯ menu, which should instead float near the ⋯ icon the way the pre-#326 Draft ⋯ menu (`.daymark-menu`) already did. Since the panel has to stay a DOM sibling of the card's own clickable button (interactive content can't validly nest inside another `<button>`) rather than a descendant of the ⋯ trigger, and the trigger itself — unlike the Draft menu's own absolutely-pinned button — sits inline in the interaction row wherever that row's content happens to place it, CSS alone can't anchor a floating panel to it the way `.daymark-menu` anchors to `.daymark-recent__menubtn`. New `positionOverflowPanel()` (`assets/app.js`) measures the trigger's and the panel's nearest `position: relative` ancestor's bounding rects on every open (`.daymark-recent__item-wrap` on a Timeline card; `.daymark-postview-meta` on `PostScreen`, which gained `position: relative` for exactly this) and writes plain `top`/`right` inline styles — `.daymark-recent__overflowmenu` itself switched from the growing-frame CSS to `.daymark-menu`'s own floating box-shadow/border treatment. The Routing popover is untouched. **Header spacing/sizing**: `.daymark-topbar`'s vertical padding and the Timeline rail's own start flourish (`.daymark-timeline-flourish--start`) both trimmed slightly to close the gap between the header and the Timeline's first item, continuing the same "reduce header-to-first-item whitespace" goal issue #213 pursued (that fix reached the pull-to-refresh indicator; this reaches the flourish sitting above it). `.daymark-iconbtn`'s base rule dropped its border/background, so the Notifications icon (its only remaining bare use — the Daymark icon link already carries `.daymark-iconbtn--plain`) now reads as plain/unboxed, matching the bottom nav's own tab icons. The Daymark header icon (Home's wordmark, Explore/Search/Me's icon link, and the Notifications/post-view back-link icon) and the Notifications bell both resized from 26px/20px to 22px, matching the footer nav icons' existing size — `.daymark-iconbtn--plain`'s own leading-overhang-cancelling `margin-left` recalculated to match (`22px - var(--daymark-tap-min)`, was `26px - ...`). | Mirroring the pre-existing `.daymark-menu` treatment (rather than inventing a new floating-panel mechanism) keeps "a small menu of secondary actions" behaviorally and visually consistent regardless of which ⋯ trigger opened it — a menu of actions reads as a transient popup, not as the card itself expanding, which is exactly what motivated moving these entries behind an overflow trigger in the first place (issue #326). JS-computed positioning (rather than a CSS-only anchor) was necessary specifically because the trigger and its panel can't share a simple ancestor/descendant relationship here the way the Draft menu's own button and menu do. The header fixes are one shared "chrome should read as one consistent system" goal — a boxed Notifications icon and a header icon rendering at a different size than the footer nav icons were both left over from when this chrome was built incrementally (PR #192, issue #267, issue #276) rather than against one target size decided up front. |

## Timeline card layout & chrome

| Decision | Value | Rationale |
|----------|-------|-----------|
| Timeline site icon hover tooltip (issue #181) | `renderSiteIconButton()` (`assets/app.js`, shared by a Mark's own icon and a subscription post's site icon) gained a `title` attribute — `"{site name}\n{site URL}"` — deliberately separate from the existing `aria-label`, which describes the button's click action ("Filter Timeline to...") rather than which site this is. | A screen reader needs the action; a sighted hover wants to know which site the icon actually represents, especially for a subscription whose cached name (see CLAUDE.md's own "Editable subscription site name" row) might still be unclear even after being set. `\n` is enough to get two lines out of every browser's native title tooltip, so no popover or extra markup was needed for this either. |
| Subscription card "Subscribed" chip removed | `renderSubscriptionPostCard()` (`assets/app.js`) no longer passes a `'Subscribed'` chip into `renderCardMeta()` — a subscription-post card's meta line now starts directly with the author, same as before the chip existed for a card with no author to show. The site icon (already rendered on every card, Mark or subscription post alike, with its own hover tooltip — see "Timeline site icon hover tooltip" above) is what actually distinguishes whose content it is; the text chip was redundant with it. `.daymark-chip--draft` itself is untouched — a Draft Mark's own chip still uses it. | The site owner's own stated reasoning: once every card already shows a distinguishing site icon, a second, purely textual "this isn't yours" label is redundant, and it was consuming meta-line space that could otherwise go to the author name or reading time on a card with either. Removing the call site rather than the CSS class keeps `daymark-chip--draft`'s one remaining, unrelated use (a Mark's own Draft chip) untouched. |
| Timeline rail start/end flourish (issue #191) | Home's own Timeline (`[data-recent-list]`) gets two small decorative marks bookending its existing vertical rail (the thin grey `::before` line drawn behind the list, aligned under every row's type icon) — a "sunrise" (a gradient-filled circle with three short rays) where the rail begins, a "sunset" (the same gradient circle, clipped to its top half, resting on a thin horizontal line in the rail's own grey) where it currently ends. Both use the exact sunset-gradient palette [docs/brand.md](docs/brand.md) already documents for the app icon/banner artwork (deep ember through to light gold), rather than inventing a second palette for the same brand. `timelineStartFlourish()`/`timelineEndFlourish()` (`assets/app.js`) render them as plain siblings of `[data-recent-list]` — immediately before it and after the sentinel/"Load more" paragraph — not as children inside it, so `loadMorePage()`'s `insertAdjacentHTML('beforeend', …)` appends (infinite scroll) can never land after the end flourish and separate it from the very bottom of the section. Both are `aria-hidden` (purely decorative) and hidden by CSS (`.daymark-timeline-flourish`) until `.daymark-recent:has([data-recent-list] .daymark-recent__typeicon)` matches — the same condition the rail itself already gates on — so neither one ever floats above/below a genuinely empty Timeline (its "Nothing here yet…" empty state, or the loading skeleton, before any real item has rendered). Scoped to Home's own Timeline only, not Search/Explore/Drafts/Me's other `.daymark-recent__list` renderings that share the same rail mechanic — this is specifically about bookending *the* Timeline, not every list that happens to look like one. | Directly the requested whimsy, deliberately tied to the *literal* meaning of the product's own name rather than a generic decorative flourish: a Daymark traditionally marks a stretch of time (dawn to dusk), and this bookends the Timeline itself the same way, in the app's own established brand gradient. Rendering the caps as siblings of the list (rather than its first/last children) was the one non-obvious design constraint — the list's own content is repeatedly replaced/appended by `loadRecent()`/`loadMorePage()`, so anything meant to stay fixed at the true top/bottom of the *section* has to live outside the part of the DOM those methods ever touch. |
| Timeline card media slot dropped entirely when there's nothing to show (issue #219) | `renderCardMedia()` (`assets/app.js`) already returned no slot at all for 'note'/'link' kinds; this extends the same treatment to any non-media kind (article/standard) that has no real image source (`item.thumbnail`/`featured_image_url`/`site_icon_url` all empty) — previously it fell through to a manufactured placeholder glyph regardless. The media-dominant kinds (image/video/gallery/mixed) keep their existing placeholder when they have no thumbnail, and so does audio specifically (carved out alongside them via a new `wantsPlaceholder` check) — both cases the existing docblock already explains: a video/audio Mark very often has no image at all, so the placeholder stands in for media the reader would otherwise expect. An article/standard card with nothing real to show has no such expectation, so the slot is dropped and the title/excerpt/date reclaim its width, via `.daymark-recent__body`'s existing flex-shrink + `min-width: 0` behavior (no CSS change needed — the body already forces itself to fill whatever's left once a sibling only reserves what it needs). | The placeholder's whole purpose (per its own docblock) is standing in for expected media a kind's own nature implies — a card that isn't image/video/gallery/mixed/audio carries no such implication, so manufacturing an icon there was reserving space for nothing. Keeping the media-dominant kinds' and audio's existing placeholder behavior untouched (rather than dropping placeholders everywhere) preserves the one case where it's still doing real work: signaling "this is a video/audio Mark, it's just missing its poster frame" rather than looking like a broken or empty card. |
| Timeline card excerpt no longer line-clamped | `.daymark-recent__excerpt` (`assets/app.css`) dropped its `overflow: hidden`/`text-overflow: ellipsis`/`white-space: nowrap` (a single-line clamp) and the `.daymark-recent__item--article` override's `-webkit-line-clamp: 2` — the excerpt now wraps and displays in full, however many lines that takes, instead of being cut off at a fixed 1-2 lines regardless of how much real text the server actually sent. No server change: a subscription post's excerpt was already up to ~40 words (`wp_trim_words( $description, 40 )`, `Daymark_Subscription_Source_Feed::normalize()`) — the truncation being reported was purely this CSS clamp cutting a card's *display* short, not a data gap. Tracked alongside a separate, larger idea (issue #224) for eventually generating a purpose-written AI summary instead of the feed's own raw excerpt text — this fix stands on its own regardless of whether that ships. | A fixed line-clamp is an arbitrary display constraint, not a reason to withhold content the server already decided was worth sending — removing it costs nothing (no truncation logic to maintain, no server change) and directly serves "give a better sense of what's in the full post before expanding it," the same goal the AI-summary idea (#224) was proposed to solve, just without inventing anything new. |
| Subscription post card's top meta line no longer shows its author (issue #285) | `renderCardMeta()` (`assets/app.js`) previously included a subscription post's `item.author` (a Draft chip, then the author, then a reading-time estimate). The author entry is removed outright — the chip and reading-time entries are unaffected. | For most single-author sites the byline reads the same as, or very close to, the site name — already shown on the card's own bottom row (`renderCardTimestampRow()`, "Site name on the date row" in this file's "Timeline polish batches" section below) and via the site icon's own hover tooltip (issue #181). Repeating a site's identity a third time directly under the title added nothing a reader didn't already have. |
| Timeline stat-row/timestamp row no longer indented under a card's thumbnail (issue #309) | A card whose kind sits a small thumbnail beside its title (article with a featured image, audio/podcast, a subscription post's site-icon fallback) had its stats (`.daymark-item-stats`) and site-name/date (`.daymark-recent__timestamprow`) rows nested inside `.daymark-recent__body` — the same flex column sitting *beside* the thumbnail in `.daymark-recent__item`'s base row layout — so both rows were indented under the thumbnail's own width too, reading as shifted right compared to a thumbnail-less card (note/link/a short article with no image), whose stats already sit flush with the card's own padding. Both rows now render as a new sibling, `.daymark-recent__footer` (`renderMarkCore()`/`renderSubscriptionPostCard()`, `assets/app.js`), which wraps onto its own full-width line — `.daymark-recent__item` is now `flex-wrap: wrap` with a two-value row/column `gap` (a smaller row-gap above the wrapped footer line, the pre-existing wider column-gap between the thumbnail and body on the line above it) and `.daymark-recent__footer` itself carries `flex-basis: 100%` to force that wrap — regardless of whatever thumbnail width (if any) precedes it on the line above: never a fixed pixel offset tied to one particular thumbnail size (48px default, 56px audio, a placeholder's own smaller intrinsic size). `.daymark-recent__body` gained `flex: 1 1 0%` (instead of the default `flex: 0 1 auto`) — necessary once the container became `flex-wrap: wrap`: a flex-wrap container decides whether an item fits on its current line using that item's *hypothetical* size, which for the default auto basis on a block box with wrappable text is its max-content width (a long, un-wrapped title+excerpt, easily wider than the whole card) — without `flex-basis: 0%` that pushed body onto a line of its own, under the thumbnail instead of beside it, the opposite of the fix. A media-dominant kind (image/gallery/video/mixed) needed matching padding moved from `.daymark-recent__body` onto the new `.daymark-recent__footer` (that modifier drops `.daymark-recent__item`'s own padding so its banner runs edge-to-edge, so body/footer each carry their own instead) but no wrap-related change — its own thumbnail is already a full-width banner stacked above via `flex-direction: column`, not a row sibling. `tests/visual/timeline-cards.html` (a pre-existing, uncommitted-to-CI manual layout fixture) was updated to render every card kind's own footer, since it's the one place a reviewer can compare every kind's stat-row alignment side by side without a live WordPress install. | Reported directly against a real subscribed podcast feed's card. Wrapping onto a dedicated line (rather than a negative-margin trick canceling a *specific* thumbnail width, this codebase's usual "cancel a sibling's reserved space" pattern — see the Explore/Search/Me header-icon rows) was the deliberate choice here: a thumbnail's width genuinely varies by kind (48px default, 56px audio, an unsized placeholder glyph for a Mark with no artwork), so a fixed cancellation value would have been exactly right for one case and wrong for every other — confirmed by first prototyping the negative-margin approach and finding it broke the audio-with-no-artwork case, which needed only ~20px canceled, not 48–56px. `flex-basis: 100%` doesn't have that problem: it forces the footer onto a new line whose left edge is simply the container's own content-box edge, unconditionally. |
| Media-dominant cards had double the trailing whitespace below the site-name row (issue #330) | Reported directly, comparing two of the reporter's own Marks — one row-layout kind (a small thumb beside the text), one media-dominant kind (a full-width banner). Measured via `tests/visual/timeline-cards.html` (a headless-rendered fixture already covering every card kind, extended for this investigation with a one-off Playwright measurement script — not committed, since the fixture itself is the durable artifact): every kind's *internal* footer gaps (body→stats, stats→timestamp, horizontal position) already matched exactly, but the whitespace *after* the site-name/date row, before the card's own bottom edge, measured 9px for row-layout kinds (audio/note/article/link/standard) versus 17px for media-dominant kinds (image/gallery/video/mixed) — double. Root cause: `.daymark-recent__item--image .daymark-recent__footer` (and its gallery/video/mixed siblings) set their own bottom padding to `--daymark-spacing-md` (16px) instead of `--daymark-spacing-sm` (8px) — the value `.daymark-recent__item`'s own base rule already uses as its bottom padding for every row-layout kind. This predates the footer-as-sibling layout ("Timeline stat-row/timestamp row no longer indented under a card's thumbnail," issue #309, above) — it carried the footer's own pre-refactor trailing-space value forward unexamined rather than re-deriving it from the row-layout kinds' own end-of-card padding. Fixed by changing that one value to `--daymark-spacing-sm`; re-measured after the fix, every kind now reports the identical 9px. | The internal footer gaps were never the problem — this is the one remaining place a media-dominant card's own trailing space diverged from every other kind's, found only by measuring rendered pixels rather than reasoning about the CSS, the same lesson CLAUDE.md's own "Explore/Search/Me header icon left-edge alignment" (issue #276) row already drew: a value meant to be identical across kinds is worth verifying that way, not just visually approximated. Matching the row-layout kinds' own existing bottom-padding value (rather than picking a new one for both) preserves the appearance of every kind that wasn't reported as wrong. |

## Interaction / stat row

| Decision | Value | Rationale |
|----------|-------|-----------|

Not independently confirmed against a live iOS device in this environment (no iOS hardware/simulator access here) — reasoned entirely from the exact reported symptom against the existing `.daymark-sheet`/`.daymark-sheet__panel` CSS, the same "researched against the reported symptom, flagged for Jeff to verify" posture already established elsewhere in this file for several other environment-constrained diagnoses. | The Visual Viewport API is the standard, purpose-built mechanism for exactly this class of problem — it reports the actually-visible area directly, keyboard included, without needing to reason about which iOS version does or doesn't support `dvh`/`svh`/`lvh` CSS units or how reliably each behaves around a keyboard transition. One shared function called from every sheet's `show()` plus two boot-level listeners (rather than per-sheet keyboard-handling code) matches this codebase's standing "one shared mechanism, not a per-feature variant" preference — the same instinct already applied to `addPickedFiles()`, `resolve_target_url()`/`target_url_markup()`, and `loadDraftIntoState()` elsewhere in this file. Changing `.daymark-sheet__panel`'s unit from `vh` to `%` (rather than leaving it and only fixing the parent) was necessary to actually close the gap: a `vh`-based child ignores its own parent's corrected height entirely, so only a percentage value benefits from the JS fix at all. |
