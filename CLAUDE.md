not even when CI is green, review is approved, or the user previously approved

## Working agreement: changelog entries

Every PR with a user-facing change must add a `CHANGELOG.md` entry under
`## [Unreleased]`, in the same PR — see CONTRIBUTING.md's Changelog section
for the full format ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
category order, the PR-link convention). Keep the entry itself short — a
sentence or two, not a design writeup: the linked PR is where full detail
lives, so the entry only needs to say what changed and, briefly, why it
matters. Also paste that same entry verbatim into the PR template's own
`## Changelog` section — this repo squash-merges using the PR title and
description as the commit message, so this keeps `git log` on `main` as
scannable as the changelog itself instead of relying on whatever length of
prose the rest of the description happens to be.

## Mission

> Make publishing to your own WordPress site feel as joyful, immediate, and
> effortless as posting to the best mobile social apps, while ensuring
> everything you create remains yours.

This is the lens for every product and design decision in this repo — weigh a
new feature, a UI direction, or a PR against this sentence before anything
else. The eight product principles below are how it gets operationalized in
the codebase; the Path/Day One/WordPress/modern-PWA rubric in
[docs/design-principles.md](docs/design-principles.md) is how it gets
operationalized in *feel*; the Non-goals list is its enforced boundary. The
"Strategic line" at the end of this file is the same idea compressed into a
competitive-positioning tagline, not a separate or competing statement.

## Key architectural decisions

Document decisions here as they are made. This is the authoritative record.

| Decision | Value | Rationale |
|----------|-------|-----------|
| Content model | Standard `post` post type | Portability; standard feeds/comments/templates |
| Custom post type | Not used | Deactivation safety; standard theme compat |
| Route strategy | Rewrite rule + `template_include` on a `daymark_app` query var | No page dependency; full control of app-shell markup (no theme chrome); clean `/daymark` PWA scope. `/daymark`, `/daymark/notifications`, `/daymark/explore`, `/daymark/search`, and `/daymark/me` are all real server routes to the same app shell (`Daymark_Routes::SCREENS`), so a direct link or a browser refresh lands correctly on any of them; Create/Publish/Success stay pure client-side hash states layered on top of Home. There are no public content pages of any kind — see "Content-type & Timeline pages removed". |
| Block vs shortcode | **Removed** (bottom nav rework) — the `daymark/*` blocks, `[daymark_*]` shortcodes, `Daymark_Renderer`, and the `@wordpress/scripts` block-editor build (`src/`, `build/`) existed only to power the retired Images/Videos/Audio/Notes section pages. With those pages gone, nothing registers a block or a shortcode anymore, and the app shell has no compiled JS at all. | Once the four content-type pages were removed there was nothing left for this system to render; keeping an unused block-editor build step around would be dead weight, not a hedge. A future block would restart this row from scratch. |
| WP 7.0 AI path | **Real** — `WordPress\AiClient\AiClient` via `wp_ai_client_prompt()`; provider Anthropic (first configured). Mock fallback when no provider is configured or any call fails. | Plugin requires WP 7.0+, so the AI Client is assumed present (no class/function existence shims). Detection: `wp_supports_ai()` + ≥1 `isProviderConfigured()`. Never throws, never blocks publishing. Legacy `WP_AI_Client` name does not exist — do not use it for calls. |
| JS framework | App shell: vanilla ES2020, no build step, no framework. | No npm required for end users, and (since the block-editor build was retired — see "Block vs shortcode" above) no build step for contributors either. |
| Brand colors | Sunset: primary `#C93A06`, deep `#9E2A02`, light `#FFD9A8`, transparent `rgba(201, 58, 6, 0.12)` | Documented in [docs/brand.md](docs/brand.md) and applied throughout the app shell (`--daymark-accent*` custom props), views, manifest, theme-color, and icon. Banner and icon artwork carry the range as a red-to-gold gradient. |
| Destination visibility | Only **connected** connectors are offered as publish destinations; auto-applied type defaults filter to connected too (explicit API selections honored as-is). AI Assist UI only renders when a provider `is_available()`. No demo-mode filter — the site itself is always the canonical destination. | A destination that can't publish or return replies shouldn't be offered. No connector ships in-repo; the connector interface + `daymark_register_connectors` hook is the extension point and is covered by PHPUnit (`test-syndication.php`), not E2E. Model defaults stay recorded in `_daymark_default_destinations`. |
| Companion connectors removed | The `moment-connector-bluesky`/`-mastodon` plugins (pre-rename naming) were removed from the repo (not published to wp.org). Real syndication rides on existing ecosystem plugins instead: publicize-style plugins via `Daymark_Publish_Helpers` (awareness + per-Mark toggles) and federation plugins via `Daymark_Federated_Comments`. ATmosphere is a controllable toggle (its documented `atmosphere_disabled` opt-out meta), so Bluesky gets an in-app on/off when ATmosphere is connected and auto-publishing. | Leaner repo; aligns with the "no real social API publishing in core" non-goal. The open connector hook remains for any plugin to register a first-class destination. |
| Destination memory | Explicit per-type selections are remembered in `daymark_destination_prefs` user meta and win over model defaults on the next publish of that type (explicit empty = "none" is remembered too). | Publishing habits differ per person and per content type; `Daymark_Publisher::get_effective_defaults()` is the single resolution point used by both the app shell and the publisher's no-selection fallback. |
| Automatic backflow | Replies sync without user action: hourly WP-Cron (`daymark_backflow_sync`) over recent Marks with real `backflow_supported` references, plus an async freshen when notifications are viewed (staleness transient, `daymark_backflow_freshen_window`). Mock references never auto-sync. Per-post 10-min cooldown; look-back window `daymark_backflow_sync_days` (14). | Real-time-or-automatic beats a manual sync button; push channels (federation plugins) are already live, so this covers only the API-polling connectors. Schedule self-heals on init for already-active installs. |
| Rename to Daymark (0.6.0) | The plugin shipped as **Moment** through 0.5.0; wp.org review did not approve that name and approved **Daymark**. Posts are now **Marks**. Every identifier renamed (slug, text domain, REST `daymark/v1` + `marks` resource, blocks `daymark/*`, shortcodes `[daymark_*]`, hooks/meta `daymark_`/`_daymark_*` with marker `_daymark_is_mark`, classes `Daymark_*`, route `/daymark`) with **no back-compat bridges**. `Daymark_Migration` (guarded on the legacy `moment_version` option, run from activation + init@5) converted old installs in place — options, user meta, post/comment meta, section-page markup. Retired: soft-deprecated in 0.7.0, removed in 0.9.0, along with `uninstall.php`'s legacy `moment_*` cleanup block and `tests/test-migration.php` ([#36](https://github.com/jeffpaul/daymark/issues/36)). A site still on Moment (≤ 0.5.0) must upgrade through an intermediate 0.6.x–0.8.x release before jumping to 0.9.0 or later — there is no direct-jump conversion path anymore. | wp.org naming requirement; "moment" also collides with core's bundled Moment.js. Changelog history before 0.6.0 stays verbatim under the old name. |
| App URL is /daymark only (Unreleased) | `/daymark` (or `/daymark-app` when that slug is already owned by real site content) is the app's only real base, on fresh **and** migrated installs alike — `Daymark_Migration` no longer carries a migrated install's old Moment-era base (e.g. `moment`) into `daymark_app_base`. Instead it's kept under its own `daymark_legacy_app_base` option purely so `Daymark_Routes` can 301 that old URL (and any already-installed home-screen icon pointing at it) to wherever the app lives now. | The rename's own promise ("a home-screen-installed app URL should not move underneath its users") doesn't require the *old brand's slug* to keep serving the app forever — a transparent redirect honors that promise without leaving `/moment` as a second, parallel home for the app. |
| Federation backflow | `Daymark_Federated_Comments` labels replies delivered by ActivityPub (`protocol=activitypub`), ATmosphere (`protocol=atproto`), and Webmention (`protocol=webmention`) plugins at read time in notifications; reaction comment types (like/repost) are excluded (`type=comment` query). `Daymark_Syndication_Links` renders `u-syndication` markup on singular Mark posts for Bridgy backfeed. | Federation plugins store replies as native WP comments — Mark's storage model — so push-based backflow needs only labeling, not import. No dependency on the plugins; pure comment-meta detection (schemas verified from plugin source). |
| Subscriptions data model (issue #78) | `daymark_subscription` is a **custom DB table** (config: URL, feed URL, status, failure count, timestamps). `daymark_subscription_post` (cached content) is a **CPT** — the one deliberate exception to "Custom post type: Not used" above. | The "no CPT" rationale is about a Mark's own portability/deactivation-safety/theme-compat, none of which applies to someone else's cached, prune-able feed content. Unsubscribing relies on WordPress's own trash-and-7-day-retention lifecycle, and Timeline's date-sorted merge with Marks needs one `WP_Query` across both post types — both are free on a CPT and hand-built on a table. |
| Subscriptions polling cron (issue #78) | WP-Cron, matching the existing `daymark_backflow_sync` pattern. Not Action Scheduler. | Zero new dependencies, and this exact problem shape (periodic polling over a growing external set) already works on WP-Cron for backflow. Action Scheduler is tracked as a future option in [issue #79](https://github.com/jeffpaul/daymark/issues/79) if real usage shows WP-Cron isn't holding up. |
| Subscriptions favicon retrieval (issue #78) | Discover via `<link rel="icon">` in the site's `<head>` (the same fetch already made for feed autodiscovery), falling back to `/favicon.ico`. | Reuses a fetch that's already happening rather than adding a second request or a third-party favicon service, which would leak subscription targets to an external party. |
| Subscriptions `rel=me` config (issue #78) | Lives on WordPress's own native profile screen (Users → Your Profile) as user meta, not a new Daymark app-shell screen. `Daymark_Microformats` reads it when rendering h-card markup. | No existing app-shell screen fits it, and building one is real UI work for a single settings field. Format validation only this phase — no reciprocal-link verification. |
| POSSE-quality outbound microformats2 markup (issue #78) | Lives in a dedicated `Daymark_Microformats` class. A Mark's own permalink page is rendered by the active theme, so this hooks `post_class`/`the_title`/`the_content` the same way `Daymark_Syndication_Links` already does for that same theme-rendered path — unrelated to (and unaffected by) the app shell's own Timeline/Explore/Search/Me views. | Keeps the singular-permalink markup concern in its own class with its own hook surface, matching the precedent `Daymark_Syndication_Links` already set. |
| Content-type & Timeline pages removed (issue #78; bottom nav rework) | No Daymark-generated public page exists anymore. The `/timeline` section page, the `daymark/timeline` block, and the `[daymark_timeline]` shortcode were removed first (issue #78): `Daymark_Plugin::remove_public_timeline_page()` (hooked on `init` at priority 5) hard-deletes an existing install's page — a genuine, deliberate exception to "never deletes user content," scoped to a page verified to still carry Daymark's own generated markup. Real 404, no redirect. The Images/Videos/Audio/Notes section pages (and their `daymark/*` blocks and `[daymark_*]` shortcodes) followed in the bottom nav rework: `Daymark_Plugin::migrate_content_type_pages()` (same `init@5` hook, same Daymark-markup verification) *trashes* — never hard-deletes — a confirmed page and records its slug in `daymark_legacy_content_pages`, so `Daymark_Routes` can 301 a bookmarked/indexed old URL to `/daymark/explore` instead of leaving a bare 404. Individual Mark permalinks and the site's own RSS/Atom feed are unaffected either way. `daymark_pages` (the page-ID map both migrations read from) is deleted outright once empty rather than left as `[]`. | Timeline is an interleaved, multi-source view (a user's own Marks plus subscribed sites' posts) — see "Subscriptions data model" above — that only makes sense inside the authenticated app shell; a public page under the same name showing something narrower was confusing and redundant. The four content-type pages existed to browse Marks by media type — Explore's "Browse by type" section (see "Bottom navigation" below) now covers that same need inside the app, so the 301 target is Explore rather than Timeline. Trash instead of hard-delete here (unlike Timeline) is the more conservative choice for pages a site owner may not have expected to lose. |
| Bottom navigation (Unreleased) | Persistent footer nav, same order everywhere: **Timeline, Explore, +New, Search, Me** — icon-only links (visually-hidden text + `title` for the accessible name), `aria-current="page"` + an `is-active` class on the current tab, the centered +New launcher never picking up that styling. Timeline (`/daymark`, default landing) and Notifications are unchanged. Explore, Search, and Me are new real routes (`/daymark/explore`, `/daymark/search`, `/daymark/me`) and app-shell screens. **Search** was promoted out of Home's old collapsible header search bar into its own screen/route, reusing the same `GET /timeline` query (keyword, type, source) and the shared Mark/subscription-post card rendering (`renderFeedItem()`/`onFeedListClick()` in `assets/app.js`) rather than duplicating it — Home no longer has an inline search UI. **Explore** is a deliberately minimal, non-chronological foundation: "Browse by type" (four buttons handing a type preset to Search) and "Following" (active subscriptions, handing a source preset to Search) — both built entirely on data/endpoints that already existed, no new backend. **Me** is a minimal identity screen: avatar/display name, a link into Search scoped to the user's own Marks, a view-only Drafts list (tap to resume editing; full edit/delete stays on Home's own Drafts row), and links out to Notifications, the wp-admin Subscriptions screen, and WordPress's own profile/logout — no in-app account settings, per the non-goals list. | The task was explicit that Explore/Search/Me should get real navigation, routes, and page shells without building out their full feature sets ahead of supporting infrastructure — "Browse by type"/"Following"/"Your Marks" are exactly the boundary of what's already backed by REST today. Extracting Search's list-rendering/interaction code into shared top-level functions (rather than copying it) keeps Home and Search from drifting apart the way the four content-type pages' renderer once risked. |
| Subscribe-by-URL + subscription management (issue #78) | A wp-admin screen (Settings → Daymark, `Daymark_Admin_Subscriptions`), not the app shell. Plain form posts (`admin_post_{action}`, POST-redirect-GET), gated on `edit_posts` like every other Daymark permission check — not the wp-admin-conventional `manage_options`. Also reachable via a "Subscriptions" action link on the Plugins list screen, and from the app shell's Explore (Following empty state) and Me (Subscriptions link) screens. Subscribe/unsubscribe logic is shared with the REST endpoints (`Daymark_Subscriptions::subscribe_to_site()`, `::unsubscribe()`) so neither surface's behavior can drift from the other. | The general principle this confirms (see the non-goals note below): the app shell is for day-to-day operational use — reading the Timeline, publishing content — while configuration/settings that are touched rarely belong in wp-admin instead. A future pass may migrate this into an in-app settings screen, but the two stay deliberately separate for now. |
| Composer autosave ("Autosave everything. Nothing gets lost.") | The composer autosaves in-progress work to a real server-side draft — reusing the exact same `POST /marks` / `PUT /marks/{id}` endpoints and publisher logic an explicit "Save as Draft" tap already uses, just triggered automatically (debounced on caption/alt/destination/category edits, immediately on picking media) instead of by a button. Requests carry `autosave=1`, which only changes which rate-limit bucket applies (`Daymark_Rate_Limiter::ACTION_AUTOSAVE`, independent of `ACTION_PUBLISH` so background autosave activity can never exhaust the budget for the user's own deliberate Publish/Save as Draft tap). Media is uploaded as soon as it's picked rather than waiting for Publish; once uploaded, a file is never re-sent (tracked client-side via `entry.uploadedId`, resolved from a follow-up `GET /marks/{id}`), so it's never attached twice. A `composerGeneration` counter guards against a slow autosave response landing after the composer has moved on to a different Mark. | Extends principles 2 and 8 (your site is the source of truth; every daymark is portable) to the drafting process itself: in-progress work should be exactly as safe as published work, without inventing a second, client-only storage format. Originally the *online* half only; the offline half is now covered by "Offline-first creation" below, which autosave falls back to via the same `submitOrQueue()` used by a real Publish/Save as Draft — see that row for the offline mechanism. |
| Notifications reply-box protection | Typed-but-unsent reply text is kept in an in-memory `replyDrafts` map (keyed by comment ID) in `assets/app.js`, restored whenever that comment's reply box is reopened — including after switching to another comment's reply box or navigating back to Notifications. Cleared on a successful send or an explicit Cancel tap. Not persisted to the server or `localStorage` — this protects against the accidental-navigation case, not a closed tab. | A smaller instance of the same "nothing gets lost" principle applied to the one other free-text input in the app shell. A full server-side autosave (matching the composer) was judged disproportionate for a single short reply field; an in-memory guard against the realistic accidental-loss paths (switching cards, going back and returning) covers the actual risk. |
| Offline-first creation (issue #121) | "Creating while offline. Publish later. Users shouldn't care." Scoped to a composer session already open when connectivity drops (or that never had it) — not a cold load of `/daymark` itself with zero connectivity, which stays out of scope (see the non-goals note below and the roadmap's "Offline app-shell load (revisit)" item). `submitOrQueue()` in `assets/app.js` (used by autosave and `flushOfflineQueue()`'s own retries) tries the real request first; on a connectivity-shaped failure (`navigator.onLine` false, or `fetch()` itself throwing the `TypeError` browsers use for a request that never reached a server — as opposed to a well-formed HTTP error response, which is rethrown so real server/validation errors still surface normally) it stores the Mark whole — including picked media, as real Blobs, which IndexedDB supports natively — in a `daymark-offline` IndexedDB database instead. (A deliberate Publish/Save-as-Draft tap itself no longer goes through `submitOrQueue()` at all — see "Optimistic publishing" below, which queues first regardless of connectivity.) `flushOfflineQueue()` replays every queued item through the exact same `POST /marks`/`PUT /marks/{id}` endpoints on the `online` event and once at boot, so the server never sees a different code path for offline-originated work; an item currently open in the composer is skipped by the background flush (its own autosave/publish handles it) to avoid racing in-memory edits newer than the last IndexedDB write. A Home "Pending" section (`renderPendingItem()`/`refreshPendingSection()`) lists what's still queued, and `openPendingMark()` resumes one in the composer, rehydrating picked files from their stored Blobs. `buildMarkPayload()` (a plain, structured-cloneable object) is the one field-mapping shared by a live request, an autosave, and a queued replay; `payloadToFormData()` is the one place that turns it into the multipart body all three send. | Directly the requested product concept, scoped narrowly on purpose: "resilient drafting" (per issue #121's own framing) rather than "full offline app". Reuses the exact publisher/REST code path online creation already uses — no server changes at all — so offline-originated content is indistinguishable from online-originated content the moment it lands. The `online` event (not the Background Sync API) is the sync trigger specifically because Safari/iOS has zero Background Sync support, and this is a phone-first PWA that documents iOS Safari as a baseline target. |

Reading time and AI tags aren't gated behind a disable filter — neither is personally sensitive the way a device's exact location, its weather, or its owner's camera equipment can be. | Everything here follows directly from "don't make users fill those in," and reuses exactly the mechanisms this codebase already trusts for that shape of problem: `buildMarkPayload()`/`payloadToFormData()` as the one payload choke point (same reasoning as Composer autosave/Offline-first creation above), the `*Edited` flag convention for "never clobber a hand-edited value," and a new single-capability `/ai/*` REST route matching `/ai/title`/`/ai/alt-text`/`/ai/transcript`'s existing shape rather than piggybacking on the heavier `/ai/suggestions` bundle (which would also generate — and waste — a caption/title suggestion nobody asked for here). Choosing a keyless weather API extends the spirit of the "no AI provider API key storage" non-goal to the one other external service this feature needed, rather than treating that non-goal as AI-only. One deliberate deviation from "just capture it": a Mark's exact quietly-captured GPS coordinates are stored (so the authenticated app/REST summary can use them) but are **not** rendered into the public, search-indexable permalink page by default — gated behind a new `daymark_publish_location_publicly` filter, defaulting to false. This matches a boundary `Daymark_Microformats` already draws for itself (its own docblock explains why `u-email` is deliberately left off the h-card): capturing a location quietly so the author's own app can use it is a different decision from publishing an author's precise device location to the public web, and "quiet capture" should never silently become "quiet publish" of something this sensitive. |
| wp-admin entry points (Unreleased) | A new `Daymark_Admin_Bar` class adds two admin bar shortcuts, both gated on `edit_posts`: "Open Daymark" as a sibling of "Visit Site" under the site-name node (top-left of the bar), and "Daymark" under the "+New" menu, which jumps straight into the composer pre-set to an **image** Mark. | WebSub/PubSubHubbub subscribing (issue #82) | Purely additive to the existing polling cron, never a replacement for it: `Daymark_Websub_Subscriber::maybe_subscribe()`, called from `Daymark_Subscription_Poller::poll_subscription()` right after a successful poll, checks the feed's already-parsed SimplePie object for a `<link rel="hub">` (`Daymark_Subscription_Source_Feed::get_last_hub_url()`, populated by the same `fetch()`/new `parse_raw_feed_body()` call the poll already made — no extra request) and, where one is advertised, sends a `hub.mode=subscribe` request with a fresh per-subscription HMAC secret and a callback pointed at a new public REST route, `Daymark_Websub_Endpoint` (`/daymark/v1/websub/{id}`). That endpoint's GET handler answers the hub's verification challenge only when the subscription is genuinely `pending` for the exact topic asked about (anyone can request the URL; that match against known state is what actually authorizes it); its POST handler verifies the delivered body's `X-Hub-Signature-256` HMAC against the stored secret with `hash_equals()` before trusting anything in it, then parses and ingests through the exact same `normalize()`/`maybe_ingest_item()` path a poll already uses — no parallel content pipeline. The `daymark_subscriptions` schema (bumped to 1.3.0) gained `websub_hub_url`/`websub_status` (`none`/`pending`/`verified`/`failed`)/`websub_lease_expires_at`/`websub_secret`; renewal re-subscribes once the granted lease is within a filterable window of expiring. The regular polling cron is deliberately left running unchanged for every subscription regardless of WebSub status — a lapsed, failed, or never-attempted WebSub subscription just means content arrives on the next poll as it always has, never a lost update. | A hub push is strictly a latency improvement layered on top of polling, not a second, independent delivery guarantee to build and maintain — reusing the poll's own ingest path (rather than a WebSub-specific one) means a delivered item is indistinguishable from a polled one the moment it lands, and the poll cycle's own dedup-by-permalink naturally no-ops whatever a hub already pushed. The verification-challenge response bypasses the REST API's JSON envelope (`rest_pre_serve_request`, matching the precedent `Daymark_REST_Controller::maybe_serve_opml_export()` already set for the same filter) because the WebSub spec requires the hub's challenge string back byte-for-byte, not JSON-quoted. |
| Webmention: rescoped to lean on ecosystem plugins (issue #83) | Issue #83 as filed asked for a full native Webmention sender, a receiving endpoint, spec verification, and Vouch spam-mitigation — reimplementing a federation protocol Daymark already made a deliberate, documented choice not to own (see "Federation backflow" above: `Daymark_Federated_Comments` does zero Webmention/ActivityPub/AT-Proto protocol work today, just reading a `protocol` comment-meta key those plugins already write). Rescoped to the one genuinely new Daymark-owned piece: composing a reply from a subscribed post. A new README.md/readme.txt FAQ callout recommends installing the Webmention plugin (and ActivityPub/ATmosphere alongside it) for the full round-trip. | Every piece of issue #83's literal ask that isn't "compose a reply" is either already solved by an existing, maintained ecosystem plugin (receiving) or would duplicate one (sending) — building it natively would mean Daymark owning security-sensitive protocol/spam-filtering code with no compensating benefit over "install the Webmention plugin," which `docs/roadmap.md` already names as a recognized alternative pattern for protocol-level features (its own deferred "admin page recommending complementary IndieWeb plugins" item). Reusing `pendingType`'s one-shot state-seeding convention for `replyTo` (rather than inventing a third mechanism) keeps the composer's "external trigger seeds initial state" story to one pattern regardless of which external trigger fired it. |
| Microformats2 (h-entry/h-card) subscription parsing (issue #84) | A new `Daymark_Subscription_Source_Microformats` connector — implementing the same `Daymark_Subscription_Source` interface `Daymark_Subscription_Source_Feed` does, registered second in `Daymark_Subscription_Source_Registry::register_built_in_sources()` — discovers and parses h-feed/h-entry markup directly from a subscribed site's pages. Registration order is what implements the documented precedence rule: `discover_feeds()` returns the first non-empty `discover()` result in registration order, so a site exposing both a traditional feed and h-feed markup is always subscribed via the feed source; the microformats source only ever wins discovery for a site with h-feed/h-entry markup but no discoverable feed at all. `discover_feeds()` now also tags each returned candidate with its producing source's own ID under `source_type`, so `Daymark_Subscriptions::subscribe_to_site()` records the right value instead of hardcoding `'feed'`. Parsing is a deliberately minimal, purpose-built regex-based tag-depth scanner (`find_elements_by_class()`, matching the lightweight, DOMDocument-free style `Daymark_Subscription_Source_Feed`'s own `<link>` autodiscovery already uses) rather than the `mf2/mf2` library the issue suggested — researched and rejected as a new dependency: CC0-licensed and historically well-used, but its last tagged release is v0.5.0 from February 2022, with an announced 0.6.0 that never shipped, a real ongoing-maintenance liability for a wordpress.org plugin that has never needed a `vendor/` directory. The scanner tracks tag nesting well enough to bound each h-entry (and each property within it) to its own matching closing tag, including void elements (`<img>` etc., which can carry a property class like `u-photo` without ever opening a nesting level) and a nested compound object (an author `h-card`, a quoted `h-cite`) — the latter's own properties are excluded from the outer entry's property search (`strip_nested_compound_objects()`) so e.g. an author's own avatar `u-photo` is never mistaken for one of the entry's own photos. h-entry post types (reply/like/repost/bookmark/rsvp, via the IndieWeb post-type-discovery algorithm's class tokens) are detected and, when an entry carries none of `p-name`, given a sensible fallback title (e.g. "Like") rather than an empty one; `post_format` itself is still derived purely from explicit `u-photo`/`u-video`/`u-audio` counts, matching how the feed source weighs media, since Daymark's Timeline does not render the reply/like/repost semantic distinctly. Normalizes into the exact same eight-key source-agnostic shape the feed source produces, so ingest/caching/Timeline code needs no changes to consume either source. | Directly closes the acceptance criteria issue #84 asked for (h-feed/h-entry parsing, h-feed-only subscribing, a documented precedence rule, post-type mapping) without taking on a stale dependency — the same "reuse what's already happening, no new dependency" instinct `sniff_content_media()` already established for this exact problem shape (see "Subscription content-type inference" below). Registration-order precedence needed no new registry mechanism: `discover_feeds()`'s existing first-non-empty-wins behavior already does exactly what the precedence rule asks for once the built-in sources are registered in the right order. Excluding nested h-card/h-cite properties (rather than a fully spec-complete implied-value/nesting implementation) is the same "minimal subset" tradeoff the class docblock names up front — sufficient to avoid the one common, meaningfully wrong outcome (an author's own photo/name leaking onto their post) without taking on full mf2 nesting-rule complexity. |

| Prefer the WordPress REST API for WP-to-WP subscriptions (issue #137) | A new `Daymark_Subscription_Source_WordPress` connector, registered **first** of all built-in sources in `Daymark_Subscription_Source_Registry::register_built_in_sources()` — ahead of both `feed` and `microformats`. `discover()` finds the `<link rel="https://api.w.org/">` REST API root a WordPress theme's `<head>` always advertises (the same discovery mechanism, and the same lightweight regex `<head>` scan, `Daymark_Subscription_Source_Feed` already uses for its own `<link rel="alternate">` feed autodiscovery), then actively probes `{root}wp/v2/posts` before trusting it — a site can disable the REST API (or that one route specifically) while leaving the discovery `<link>` in place, so presence of the tag alone is never enough to prefer this source over the existing feed connector. `discover_feeds()`'s existing first-non-empty-wins registration-order behavior (established for issue #84) is what implements "prefer the REST API over RSS/Atom" here too — no new registry mechanism needed, same as #84's own precedence rule. `fetch()` polls `wp/v2/posts?per_page=20&_embed=author,wp:featuredmedia` (embedding author name and featured-media URL in the one request, avoiding an N+1 per-post fetch); `normalize()` reads the site's real `format` field directly into `post_format` — the entire point of this source, versus the feed connector's own enclosure/content-sniffing guess — mapping the five WordPress formats with no dedicated Daymark bucket (`aside`/`link`/`quote`/`status`/`chat`) down to `standard`, the same "no natural equivalent" treatment issue #84's own unmapped h-entry post types (reply/like/repost/bookmark/rsvp) already get. Title/excerpt/author text from `wp/v2/posts`' `.rendered` fields go through `html_entity_decode()` before `sanitize_text_field()` — unlike the feed source's SimplePie accessors (which already decode entities during their own XML parsing) or mf2 markup handled the same way in `Daymark_Subscription_Source_Microformats::plain_text()`, a REST `.rendered` field is real theme-ready HTML that arrives still entity-encoded (e.g. a title's apostrophe as `&#8217;`), so skipping the decode step would leak literal `&hellip;`-style text onto the Timeline. | Closes all four of issue #137's acceptance criteria (a working REST API is preferred over RSS/Atom, `post_format` reflects the real WordPress value rather than a guess, a site with the API disabled/unreachable/non-WordPress falls back to the feed connector unchanged, and no interface change was needed) while reusing the exact precedence mechanism (registration order in the registry) and "map an unrepresented value down to `standard`" pattern issue #84 already established, rather than inventing either a second mechanism or a second normalization convention. Actively probing `wp/v2/posts` rather than trusting the `<link>` tag's mere presence is a deliberate, issue-specified correctness requirement: a site that disables the REST API while leaving old cached HTML/CDN-served markup with the link intact would otherwise silently break subscribing to it. |

// Required post meta

_daymark_primary_type           = image|video|audio|note|gallery|mixed

_daymark_ai_assist_used         = '0' or '1'
_daymark_created_from           = 'mobile'
_daymark_transcript             = plain text (audio/video; AI-generated or hand-typed/edited)
_daymark_in_reply_to            = URL (set only via the composer's "Reply" action on a subscribed post; rendered as u-in-reply-to)

## Security checklist (apply to every endpoint and form handler)

- [ ] `current_user_can()` before any write
- [ ] Nonce verified via `X-WP-Nonce` header
- [ ] Inputs sanitized with `sanitize_text_field()` / `wp_kses_post()` / `absint()`
- [ ] MIME type validated before `wp_handle_upload()` — not just extension
- [ ] All output escaped with `esc_html()` / `esc_attr()` / `esc_url()`
- [ ] No direct DB queries without `$wpdb->prepare()`
- [ ] No unauthenticated publishing endpoints
- [ ] Expensive endpoints rate limited via `Daymark_Rate_Limiter` (AI / publish / autosave / sync actions; filter `daymark_rate_limits`)
- [ ] Uploads checked per file **and** per request total (`Daymark_Publisher::validate_file_list()`, `MAX_TOTAL_FILE_BYTES`; filter `daymark_upload_total_max_bytes`)

## Product principles

Codified September 2026; supersedes the six-item list in
[docs/planning/README.md §2](docs/planning/README.md). This is the authoritative
list — use it as the lens for future product decisions, and cite the relevant
principle in a decision's rationale when it applies. Each principle is the
Mission statement above (also September 2026) broken into a concrete
implication for the codebase.

1. **Publishing comes before editing.** The composer's job is to get a Mark
   published, not to be a content editor. Refinement (per-image alt text,
   captions, titles) is available but never blocks or gates the publish action.
2. **Your site is the source of truth.** The site is always the canonical,
   required destination; every other destination is additive syndication, never
   a replacement — see "Destination visibility" and the content model above.
3. **Mobile is the primary creation experience.** The app shell is designed
   one-handed, phone-first, touch-first — vanilla ES2020 with no build step,
   generous tap targets, no wp-admin chrome. Desktop/tablet use works but isn't
   the design target.
4. **Media is first-class.** Images, video, audio, galleries, and notes are
   equal citizens with type-specific handling (per-image alt text, type-based
   destination routing, MIME validation, upload budgets) — not an attachment
   bolted onto a text post.
5. **Everything should be publishable in under 30 seconds.** Defaults do the
   work: type-based destination preselection, remembered destination
   preferences, minimal required fields, no forced onboarding. Every new
   required field or step is a cost to be justified against this.
6. **AI assists the creator, never replaces them.** AI Assist is optional,
   additive, and never blocks publishing — no configured provider means no AI
   UI at all, every suggestion is editable before it ships, and the mock
   fallback keeps the flow identical either way.
7. **Progressive disclosure: simple by default, powerful when needed.** The
   common path (one image, one tap) stays uncluttered; less-common power
   (destination overrides, categories, block editor settings, subscription
   management) surfaces only when relevant, or is pushed to wp-admin rather
   than crowding the app shell — see the non-goals note below.
8. **Every daymark is portable and future-proof.** A Mark is always a standard
   `post` with meta — never a bespoke format — so it survives the plugin,
   theme, or host being removed. This is why Marks specifically stay off
   custom post types even though `daymark_subscription_post` (someone else's
   cached content, not a Mark) is the deliberate exception.

## Non-goals (never build these in the prototype)

- Real social API publishing
- Real social comment/reply polling or webhooks
- Custom post type (unless hard constraint appears)
- AI provider API key storage
- A plugin marketplace, or a general-purpose settings dashboard built for its own sake
- wp-admin chrome or site management features inside the Daymark app shell's own UI — the app shell stays focused on day-to-day operational use (reading the Timeline, publishing content). Infrequently-touched configuration/settings (e.g. subscription management, `rel=me`) belong in wp-admin instead, outside the app shell — see the architectural decisions table for the confirmed instances of this. Not a ban on Daymark ever having a wp-admin screen; see the row above for the current thinking on eventually migrating some of this into an in-app settings screen.
- Multi-user or team workflows beyond standard WordPress roles
- Full offline PWA mode. Narrowed (issue #121): offline **creation** is shipped — see "Offline-first creation" in the architectural decisions table — for a session already open when connectivity drops. Still out of scope: a **cold load** of `/daymark` itself with zero connectivity (the service worker's scope stays deliberately restricted to the plugin assets directory, so it can never cache the app-shell HTML or its per-request CSP nonce — widening that is its own security-sensitive decision, tracked in [issue #126](https://github.com/jeffpaul/daymark/issues/126), not assumed here) and general offline **reading** (Timeline/notifications/Explore/Search still require connectivity, conservative SW only).
- Push notifications
- A finished Explore, beyond its current "Browse by type" + "Following" foundation — memories, highlights, collections, favorites, recently-popular, and suggested accounts/content are future sections, not implied by what's there today
- Speculative AI or semantic search — Search stays keyword + explicit filters (type, author, date, tag, location, people followed are the planned filter set; only type and source exist today)

## Strategic line

WordPress does not need to become a social network.
It needs to become the best place for social-shaped content to begin.

The Mission statement at the top of this file is the same idea, stated as a
product goal rather than a competitive position — use that one as the lens
for evaluating new work.
